# FP-001: неполный присед и ограничение 2D-глубины

Статус: **подтверждённый False Positive, не устранён**. Приложение **In Development**. Дополнение существующего PR №7 от `208c4049`. Merge не выполняется.

## Факты и источник разметки

Пользователь разметил первые четыре движения в предоставленной записи экрана iPhone 15 Pro как намеренно неполные. Ожидаемое количество полных повторений — 0; на записи счётчик становится 1. Эта ручная разметка принимается как эталон данного случая и не переопределяется по углу Vision.

Локально просмотрены ключевые кадры эпизода. Запись длится около 47,05 с, размер 1180×2556; частота записи экрана около 60 FPS **не является частотой Vision**. В начале записи таймер тренировки уже показывает 00:30. Все отметки ниже относятся к времени видео, а не к таймеру приложения.

Видны отдельные условия raw/EMA и ожидание сглаженного возврата — формат диагностики, введённый в `208c4049`. Точный SHA установленной сборки на экране отсутствует.

Таким образом, переход 0 → 1 локализован между просмотренными кадрами примерно 11,24 и 11,31 с, при времени тренировки около 00:42. Это устойчивые показания ниже 105° и последующий подтверждённый возврат, а не только один короткий raw-выброс или «хвост» EMA. Выбрана правая нога. Низкий confidence левой ноги не означает потерю выбранной правой; её значения в перечисленных кадрах проходят существующий порог 0,5.

Таблица — округлённые показания HUD, вручную проверенные на кадрах. Это не полный поток `BodyPose`, не исходные timestamps захвата и не точные координаты суставов. Повторные кадры записи экрана нельзя считать отдельными наблюдениями Vision.

Изображения/видео не включаются в репозиторий. Временные кадры анализа удаляются после работы; исходный пользовательский файл не меняется. В регрессии остаются только числовые значения без изображения человека.

## Разделение причин

| Слой | Что подтверждено | Что остаётся неизвестным |
|---|---|---|
| Определение физической глубины | Ручная метка «неполное» расходится с классификацией по 2D-углу ≤105°. Этот критерий не гарантирует требуемую пользователю глубину | Какое измеримое правило физической глубины следует использовать во всех ракурсах; его нужно согласовать независимо от Vision |
| Vision / входные суставы | На экране правая нога даёт пригодные по confidence точки и устойчивый угол около 98–104° | Точность выбранных hip/knee/ankle. Панель закрывает таз/часть ноги, а исходных координат и изображения до UIKit-overlay нет. Confidence не является границей ошибки координат |
| Геометрия 2D | Код считает угол между векторами hip–knee и ankle–knee с поправкой на aspect ratio; переходы согласованы с HUD | Угол данного кадра нельзя независимо пересчитать без исходных точек и размеров camera buffer; по записи экрана ошибка арифметики/входных метаданных не доказана |
| SquatCounter | Три raw ≤105°, текущая EMA ≤105°, затем три raw ≥160° и текущая EMA ≥160° объясняют событие. Числовой компонентный replay подтверждает последовательность | Признаков нарушения контракта FSM в этом эпизоде не найдено. FSM не получает ручную метку или независимую физическую глубину и не может исправить ошибочную семантику входа |

Речь идёт о **ложном результате приложения относительно разметки**, даже если отдельная FSM правильно выполняет свои правила. Называть событие правильным приседом из-за прохождения 105° нельзя. Также нельзя объявлять ошибку Vision установленной только по наличию False Positive.

В текущих данных недостаточно оснований для достоверного production-исправления. Снижение порога, требование пригодности обеих ног, новый cooldown, отсечение ракурса по случайным расстояниям или отключение счёта только на этом фрагменте могут скрыть конкретный случай и создать новые пропуски. Такие изменения не внесены. Все Swift-файлы приложения и его пороги остаются побайтно равны `208c4049`.

## Почему одних текущих 2D-признаков недостаточно

Известный угол колена не тождественен ручной метке глубины всего приседа. Даже точный пространственный угол потребует отдельного проверенного правила сопоставления с «полное/неполное».

2D-проекция теряет компоненту глубины. Контрпример для knee в начале координат:

```text
Вариант A: hip = (0.5, 0.5, 0),          ankle = (0.5, -0.5, 0)
Вариант B: hip = (0.5, 0.5, sqrt(0.5)),  ankle = (0.5, -0.5, -sqrt(0.5))
```

Углы в пространстве — соответственно 90° и 120°. Проекции x/y совпадают и обе дают 90°. При одинаковом confidence текущий анализатор не получает признака, позволяющего различить эти варианты. Это математическая неоднозначность, а не реконструкция позы пользователя, результат запуска Vision 3D или критерий разметки реального полного приседа.

Отдельный pinhole-тест проверяет перспективу `u=x/z, v=y/z`: knee=(0,0,4), первая пара hip=(0.4,0.4,4), ankle=(0.4,-0.4,4), вторая hip=(0.46,0.46,4.6), ankle=(0.34,-0.34,3.4). Оба изображения дают одинаковые u/v и угол 90°, но пространственные углы различаются: первый 90°, второй >105°. Значит, неоднозначность не ограничена ортографической моделью.

При этом **идеальная плоская сагиттальная модель**, просто повёрнутая по yaw к фронтальному виду, обычно увеличивает видимый угол к 180°: тест для пространственного 120° и yaw 0/30/45/60/90° не даёт ≤105°. Поэтому нельзя без данных объяснить этот False Positive одним словом «фронтальный». Возможны другое пространственное положение сегментов, перспектива, ошибка локализации точек или несоответствие самого признака ручному критерию.

При укороченной проекции сегмента малое смещение точки может сильно менять угол. Синтетический тест с knee=(0.5,0.5), ankle=(0.5,0.3), hip=(0.5,0.502) даёт 180°, а с hip=(0.51,0.502) — около 101°. Это иллюстрация чувствительности, а не доказательство такого смещения в видео. Новый геометрический отсекатель или confidence-эвристика по этому примеру не вводятся.

При контролируемом боковом ракурсе 2D может оказаться пригодным эмпирическим признаком. Корректность для пользователя, камеры и заданной глубины нужно измерить; общей гарантии для всех ракурсов из текущих x/y/confidence/EMA нет.

## Регрессионные проверки

`SquatDepthValidationTests` добавляет:

1. Числовую проверку перехода 1/3 → 2/3 → lowered по прочитанным HUD raw/EMA.
2. Проверку ожидания EMA при возврате, одного события и защиты от второго счёта.
3. Требование ручной разметки: неполный цикл должен дать 0 полных повторений. Сейчас компонентный replay даёт 1; это **строгий `XCTExpectFailure` FP-001**, а не исправленная проверка.
4. Контрпример одинаковых ортографических 2D-проекций при разных 3D-углах.
5. Независимый контрпример для перспективной pinhole-проекции.
6. Проверку границы применимости идеальной yaw-модели.
7. Иллюстрацию чувствительности угла к смещению укороченного сегмента.
8. Проверку, что низкий confidence невыбранной левой ноги не аннулирует пригодную выбранную правую.

Начальное standing в компонентном replay задаётся как явная предпосылка, соответствующая видимому состоянию перед снижением. Пропущенные исходные кадры, координаты Vision и задержки камеры не фабрикуются. Replay проверяет FSM на округлённых парах; не является end-to-end воспроизведением camera → Vision и не проверяет реальную частоту доставки.

Ожидаемая ошибка видима в XCTest и отчёте. Strict-режим требует пересмотреть fixture при неожиданном прохождении. Будущий 3D/семантический путь потребует соответствующей end-to-end регрессии; одного удаления ожидаемой ошибки или изменения метки на «полное» недостаточно.

Прежний `testDoesNotCountPartialSquat` подаёт синтетический угол 130° и проверяет числовой контракт. Он не доказывает отклонение всех физически неполных движений с другими измеренными 2D-углами. Новая ручная метка намеренно независима от этого порога.

## Техническое предложение: сравнение Vision 2D и 3D

### Цель и границы

Отдельный эксперимент должен проверить, помогает ли 3D снизить подтверждённые False Positive и пропуски при неизменной ручной разметке. 3D не объявляется готовым решением и не внедряется в этот PR. Не изменяются камера, Core Data, интерфейс тренировки, модель сохранения или пороги.

Первичные API: [Vision 2D](https://developer.apple.com/documentation/vision/detecting-human-body-poses-in-images), [Vision 3D](https://developer.apple.com/documentation/vision/identifying-3d-human-body-poses-in-images), [WWDC23](https://developer.apple.com/videos/play/wwdc2023/111241/). 3D-request доступен с iOS 17 и может работать без depth metadata; depth — отдельное улучшение входа, не гарантия точности.

SDK Xcode 27.1: `VNHumanBodyRecognizedPoint3D`/`VNRecognizedPoint3D` не предоставляют такой же per-joint Float confidence, как 2D-точки. Нельзя выдумывать 3D confidence=0.5 или использовать `heightEstimation` как уверенность в коленном угле. Отсутствие наблюдения, нечисловые значения и вырожденные векторы обрабатываются явно.

### Сопоставимые входы

- Зафиксировать baseline `208c4049`, версии iOS/SDK, request revisions, формат/размер buffer, камеру, ориентацию, mirroring и временную шкалу.
- Подавать **одни и те же исходные camera buffers** обоим методам в одной локальной сессии. Запись экрана с HUD не заменяет такой вход: overlay закрывает человека и меняет изображение.
- Сначала RGB-only 2D против RGB-only 3D, без изменения capture-архитектуры. Ветку с синхронной depth рассматривать отдельно, только после проверки возможностей конкретной камеры/формата; нельзя приписывать текущей wide-angle конфигурации доступную depth автоматически.
- Брать hip/knee/ankle 3D из одной root/model системы координат (`position`), затем строить hip−knee и ankle−knee. Нельзя смешивать `localPosition` с разными parent frames.
- Не подставлять 2D вместо отсутствующего 3D и не соединять одну фазу из разных методов. У каждого метода независимые фильтр/счётчик и явный сброс непрерывности.
- Разделить измерение качества на одинаковой временной выборке и реальную производительность. Для офлайн-повтора использовать исходные capture timestamps, а не время выполнения двух запросов; для live-прогона отдельно учитывать реальную доставку и влияние бюджета 250 мс.

### Ручная разметка и матрица испытаний

До просмотра предсказаний согласовать с пользователем определение полного/неполного движения и границы цикла. Метка не выводится из угла 105° Vision. Для FP-001 исходная метка пользователя остаётся «неполное».

План пилота: обе камеры × боковой/45°/фронтальный ракурс; в каждом условии отдельные серии полных и намеренно неполных движений. Например, по 10 каждого типа на шесть условий — 120 размеченных циклов как пилот, не доказательство точности для популяции. Условия/объём, допустимое окно сопоставления и критерии приёмки фиксируются до итогового сравнения. Для обобщения нужны независимые сессии и разные участники.

Размечать начало/низ/возврат, label full/partial/uncertain, событие счёта, ракурс, камеру, видимость суставов и наблюдаемые прерывания. Намерение выполнить полный/неполный цикл и метку фактического выполнения фиксировать отдельно. При возможности второй независимый разметчик проверяет спорные случаи; согласие и число uncertain публикуются отдельно. Это не отменяет уже принятую ручную разметку текущего False Positive.

Для пилота возможны живое наблюдение и локальная числовая таблица без записи изображений. Любые измерения точности координат/3D-углов потребуют отдельной независимой опоры; одни метки повторений её не дают. Производственное приложение не начинает сохранять позы/видео в рамках этого предложения.

### Метрики и сравнение

- Сопоставление событий 1:1 с размеченными полными циклами. Событие на partial, вне циклов или дополнительное событие на уже сопоставленном цикле — FP; полный цикл без события — FN.
- Precision = TP/(TP+FP), recall = TP/(TP+FN). При нулевом знаменателе — N/A. Отдельно доля принятых partial, число двойных событий и задержка относительно размеченного возврата.
- Пропавшие наблюдения и abstention не исключают полные циклы из знаменателя recall. Coverage, разрывы, число сбросов и причины отказов показываются отдельно.
- Раздельные результаты по камере/ракурсу/типу движения, длительная сессия, фактический FPS, latency, память, нагрев. Сравнение считается парным по циклам, а не миллионам коррелированных кадров.
- Сначала изолировать влияние признака при заранее зафиксированном FSM. Не объявлять пороги 105°/160° валидными для 3D автоматически. Возможная калибровка выполняется на pilot/train; итоговые параметры блокируются до проверки независимых сессий.

Доставляемые результаты: локальная числовая таблица, правила разметки/сопоставления, матрица TP/FP/FN, отдельный разбор FP-001 и пропусков, профиль производительности и решение go/no-go. Улучшение recall без контроля False Positive не считается достаточным. Нулевой FP на конечном пилоте не гарантирует нулевой риск; критерий и оценку неопределённости нужно согласовать до проверки.

Если и более точный пространственный угол принимает те же ручные partial, переход на 3D сам по себе не решает задачу: требуется независимо проверить связь признака с согласованной физической глубиной. Новый признак/порог не подбирается по одному FP-001 и не внедряется до проверки независимых сессий.

## Фактически выполненные проверки этого дополнения

Среда: Xcode 27.1 (27A9275), SDK 27.1, проект Swift 5, deployment target iOS 17.0. Добавлены 8 тестов поверх 189; все production-файлы приложения побайтно сохранены относительно `208c4049`. Project-файл меняется только для регистрации нового XCTest-файла.

Выполнение XCTest использует Swift 5; Swift 6 проверяет компиляцию.

Новых предупреждений в добавленном тестовом файле не обнаружено. Runtime iOS 17 недоступен. Проанализирована предоставленная пользовательская запись; новая сборка агентом на физическом iPhone не запускалась.

## Решение по текущему PR

Подтверждённый False Positive остаётся открытым. Добавляются только регрессии и документация, без маскирующего production-изменения. Для достоверной коррекции нужно проверить семантику физической глубины и качество входа на независимых наблюдениях. После обновления существующего PR №7 работа останавливается без merge.
