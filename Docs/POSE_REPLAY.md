# Pose Replay — воспроизводимая проверка приседаний

## Задача

Изменять алгоритм только после сравнения на **одинаковых входных кадрах**. В этой первой версии Replay фиксирует числовые координаты hip/knee/ankle для обеих ног **после Vision 2D**, то есть поток `BodyPose` непосредственно перед `PoseAnalyzer` и `SquatCounter`. Replay воспроизводит 2D классификацию на тех же координатах и с тем же временем кадров, включая события сброса движения. Экспериментальный Vision 3D из Draft PR #26 **не входит** в эту первую версию.

## Как записать материал на iPhone

1. В Fork открыть ветку `feature/pose-replay-baseline`, в Xcode выполнить `⌘U`, затем Debug `⌘R`.
2. Установить iPhone на устойчивую опору, чтобы **всё тело и ноги** были в кадре. На первом проходе стоять боком к камере. Нажать `Старт`.
3. Нажать кнопку **REC**, прочитать предупреждение о данных о движениях тела, подтвердить `Начать запись`. Запись **не включается автоматически** и не сохраняет фотографии/видеокадры.
4. Постой 2–3 секунды, затем выполни **3 полных, 3 неполных** приседания боком. Встань неподвижно на 2–3 секунды между сериями. При необходимости повернись под 45° и повтори 3+3 (не меняй высоту телефона).
5. Нажми **STOP**, затем выбери `Сохранить в Файлы` или другую опцию системного share sheet. Получится файл `RepsCounter-PoseReplay-….json` c координатами суставов и относительными метками времени. Временный файл приложения удаляется после закрытия меню экспорта.
6. **При желании** одновременно записать экран, чтобы позднее вручную разметить каждую попытку. Видео и экспортированный JSON в GitHub автоматически не отправляются. Для анализа можно передать JSON и видео **отдельно в разговор**, если согласен поделиться числовыми данными тела.

Система записывает **максимум 1200 событий** (примерно две минуты при 10 позах/с). Дальнейшие события не добавляются до STOP. Для длинных сессий начни новый экспорт.

## Что содержит JSON

`schemaVersion: 2`, `initialState` (фаза, число ожидающих подтверждений, выбранная нога и EMA на момент REC), `events` (время от ручного начала записи, вид `pose` или `reset` и для pose: aspect ratio, угол вращения и координаты/уверенность суставов `leftHip`, `leftKnee`, `leftAnkle`, `rightHip`, `rightKnee`, `rightAnkle`), `annotations` (по умолчанию пустой массив). В данных **нет пикселей камеры, видео или аудио**, но координаты движений тела **являются персональными данными контекста тренировки**, поэтому не публикуй такие файлы в открытом репозитории без явного решения.

`annotations` — необязательные **ручные** временные границы попыток, каждая `{ "startSeconds": ..., "endSeconds": ..., "isFullSquat": true/false }`. Диапазоны неперекрывающиеся. Если приседание физически полное, но алгоритм не засчитал его — FN. Если неполное засчитано — FP. Дополнительное засчитывание в одной полноценной попытке тоже FP. События вне размеченных попыток считаются FP. Пока диапазоны не размечены, **не утверждать precision/recall по числу 2D повторов**.

## Как воспроизводится алгоритм

`PoseReplayRunner.replay(session)` восстанавливает `BodyPose`, последовательно применяет `PoseAnalyzer` и текущий `SquatCounter(maximumHipKneeHeightRatio: 0.35)`, сбрасывает движение на записанных `reset`, при паузе между пригодными позами более 250 мс и при смене/потере ноги. Выдаёт точные временные метки count и диагностические `PoseReplayDepthSample`.

В формате v2 обычный 2D продолжает движение с момента REC. Результат содержит только времена новых повторений. Разрыв, пауза, возобновление и граница подходов записывают явный `reset` в том порядке, в котором его применил рабочий счётчик. При разрыве reset предшествует позе с тем же временем; на последнем кадре подхода поза предшествует reset. Пауза входит в шкалу времени от REC, позы во время паузы не записываются.

Старые файлы v1 открываются с исходными правилами: старт из `seekingStanding`, явные сбросы и проверка интервала между пригодными позами. Начальное состояние для них неизвестно. Теневые алгоритмы в обоих форматах получают только записанные позы и сбросы; первый неполный цикл может отличаться от обычного 2D.

**Теневая проверка глубины** хранит `signedHipKneeVerticalDistance = hip.y - knee.y` по выбранной 2D ноге в нормированных координатах Vision (Y растёт вверх): значение положительно, пока **центр hip-joint выше knee-joint**; <=0 означает что эти два распознанных центра на одной высоте или тазобедренный центр ниже. Это **ещё не** биомеханический критерий «складка таза ниже верхней части колена»: 2D перспектива и неточность суставов влияют на метрику. Сравниваются **непосредственно** signed distance и старый нормализованный наклон бедра, но оба значения **не влияют на счёт**.

`PoseReplayRunner.score(result, against: annotations)` вычисляет TP, FP, FN только на вручную размеченных диапазонах. В тестовом наборе есть демонстрационные синтетические позы; они подтверждают детерминированность и корректность инфраструктуры, но **не реальную accuracy Vision**.

## Границы первой версии

- Реплей выполняется над **после-Vision 2D** наблюдениями: он не измеряет ошибки самого Vision от видеопикселей. Чтобы исследовать точность распознавания суставов, нужны визуальные референсы, полученные с отдельным явным согласием, и разметка.
- В этом PR не меняются production 2D счёт, порог 0,35, камера, Core Data или экспериментальный 3D.
- Следующим этапом после получения первого реального JSON и ручной разметки можно расширить формат до синхронных 3D числовых показателей отдельным небольшим PR (не добавлять 3D через прямое копирование 61-коммитного Draft #26).
- В Xcode обязательны `⌘U` и `Product → Build For → Profiling`; Release не содержит инструментов Replay.

## Второй этап — независимый двухногий Replay (19.11.2026)

В этой же Debug-ветке появился `PoseReplayBilateralRunner.replay(session)`. Он **не подключён к экранному счётчику, истории или Vision 3D**. На том же JSON он сначала воспроизводит исходный `PoseReplayRunner` для контрольного результата, затем независимо пропускает позы левой и правой ноги через свои `PoseAnalyzer` и `SquatCounter(maximumHipKneeHeightRatio: 0.35)` с прежними требованиями confidence, 3 кадрами подтверждения, EMA и сбросом после gap >250 мс.

Для каждого потенциального подсчёта сохраняется сторона, момент подтверждения глубины и момент завершения повторения. События от **разных ног** объединяются в одно, только если их интервалы от подтверждённой нижней фазы до возврата действительно пересекаются, а окончания разделяет не более **0,75 с**. События одной и той же ноги никогда не объединяются. Это **эвристика дедупликации**; на другом темпе и при долгом залипании фазы она может потребовать изменения по размеченным данным. Агрегатор не пересматривает критерии глубины и не выбирает «правильную» ногу по 2D confidence.

## Аудит глубины по размеченным числовым записям (20.11.2026)

В Debug реализован `PoseReplayDepthAudit.evaluate(session)`. После импорта **локального JSON с `annotations`** он показывает, насколько часто **нижняя фаза** подтверждается по каждому из трёх независимых диагностических правил:

- **Только угол:** коленный угол ≤105° минимум в трёх последовательных достоверных кадрах одной и той же ноги.
- **Текущий проекционный ТК:** угол ≤105° и `(hip.y-knee.y)/projectedThighLength ≤+0.35`, три последовательных достоверных кадра.
- **Центр hip не выше центра knee:** угол ≤105° и `hip.y-knee.y ≤0`, те же три последовательных кадра.

Для каждой ноги минимальная confidence hip/knee/ankle — 0,5. Пропуск/сброс или разрыв более 0,25 с прерывает серию. Сравниваются обе ноги независимо; признак наличия нижней фазы в размеченной попытке считается, если один из анализаторов подтвердил её. **Это не реальный FSM-count**: нет отдельной проверки возврата в стойку, EMA/фьюжна и дедупликации. Результаты нельзя интерпретировать как точный TP/FP/FN production-счётчика.

Для **двух локально размеченных** сессий 19.11.2026 (всего 24 попытки: 12 отмечены полными, 12 неполными) независимый Python-аудит этих же порогов дал:

| Правило нижней фазы | Полных с нижней фазой (из 12) | Неполных ошибочно с нижней фазой (из 12) |
| --- | ---: | ---: |
| Только угол ≤105° | 12 | 12 |
| Угол + текущий ТК ≤+0,35 | 11 | 0 |
| Угол + hip.y ≤ knee.y | 0 | 0 |

Числовые записи, суставные координаты и привязанные к ним временные метки **не добавлены в GitHub**. Приведены только агрегированные результаты. Разметка пользовательская, не измерение референтной биомеханической глубины; две сессии не охватывают проблемный ракурс и тесты от 20.11.2026. На другом ракурсе текущий ТК может ошибочно отклонять полные приседания.

**Вывод:** простое ослабление порога или замена ТК строгим `hip.y ≤ knee.y` не обоснованы. Прежде чем менять production, собрать новый **размеченный числовой Pose Replay** именно для ракурса 15–20° от фронта и повторить A/B на одних входных наблюдениях. Результаты текущей реализации оценивать через `⌘U` и импорт JSON на iPhone. Результаты XCTest/Release после этого обновления ещё не подтверждены.


## Теневой адаптивный критерий глубины (20.11.2026)

Новая функция `PoseReplayAdaptiveDepthAudit.replay(session)` доступна **только в Debug Replay**. Она не изменяет счётчик тренировки, `SquatCounter`, порог production ТК +0,35, историю, камеру, 3D и другие ветки. В результате импорта JSON отображаются `Адаптивный 2D (тень)` и `Доп. кадров глубины`; при наличии ручных annotations дополнительно показываются `Адаптивный TP/FP/FN`.

Механизм: исходная FSM и EMA остаются прежними, стандартный критерий `ТК≤+0,35` принимается без дополнительных требований. Для кадров с `+0,35 < ТК ≤+0,45` возможна **альтернативная проверка**, только если одновременно:
- обе ноги распознаны достоверно (hip/knee/ankle confidence ≥0,5), и угол каждого колена ≤105°;
- после предварительно распознанной стойки (колено ≥160°) нормализованное уменьшение вертикального расстояния hip–ankle на **каждой ноге** ≥0,34 относительно её собственной медленно обновляемой опорной высоты;
- условия выполняются **не менее трёх последовательных кадров**; сбросы и большие разрывы обнуляют накопление и стойку.

Только в локальном теневом `SquatCounter` при выполнении условий используется виртуально подтверждённый ТК=+0,35. Исходная геометрия и само наблюдение не модифицируются. Это **эвристика оценки по 2D проекции**, а не физический стандарт «складка таза ниже верхней части колена». При перекрытии второй ноги функция может не улучшать recall, потому что усиление допускается лишь при двух надёжных ногах.

## Теневое удержание выбранной ноги при кратковременной потере (20.11.2026)

В `PoseReplayAdaptiveDepthAudit.replayWithGrace(session)` добавлено **только Debug Replay**. Это отдельный вариант поверх предыдущего адаптивного анализа, который оставляет `replay(session)`, production `PoseAnalyzer` и `SquatCounter` без изменений.

- Когда ранее выбранная нога на мгновение становится ненадёжной (`confidence < 0.5` / отсутствует подходящая геометрия), при пропуске до **0,23 секунды** фиксируем отсутствие **измерения**, но не вызываем `SquatCounter.process` и не сбрасываем достигнутую фазу или ранее подтверждённые надёжные кадры.
- Если нога восстановилась до истечения `0,23 с`, продолжаем с тем же выбранным leg/EMA. Потерянные кадры не используются для подтверждения глубины или стойки, но счётчик не обнуляет фазу из-за одиночного сбоя Vision.
- При устойчивой потере или разрыве реальных надёжных измерений `>0,25 с` сохраняем обязательный сброс движения и разрешаем повторный выбор ноги. Переход на другую ногу не сшивает одно повторение между ногами без проверки.
- Экспериментальный результат отображается в импортном Debug-окне отдельными строками `Grace 2D (тень)`, `Удержано кадров ноги` и, при ручной разметке, `Grace TP/FP/FN`. Это **не** рабочий режим приложения.

### Оценка на четырёх сохранённых наборах

Результаты независимого Python-переноса той же логики. Они ещё не подтверждены импортом в обновлённый Swift Replay.

| Набор | Adaptive TP/FP/FN | Grace TP/FP/FN | Удержано кадров |
|---|---|---|---:|
| 19.11, annotated №1 | 3/0/3 | 3/0/3 | 6 |
| 19.11, annotated №2 | 4/0/2 | 4/0/2 | 13 |
| 20.11, почти фронтальный | 5/0/0 | 5/0/0 | 3 |
| 20.11, ~45°, исходная приблизительная граница 29,00 с | 4/0/1 | **4/1/1** | 6 |
| 20.11, ~45°, уточнённая по видео граница 29,35 с | 4/0/1 | **5/0/0** | 6 |

Пятый completion event из Grace произошёл в **29,070 с от REC**. В первой разметке `[26,60;29,00)` событие формально классифицировалось как FP в следующем (неглубоком) интервале. После просмотра экранной записи видно, что пятый глубокий присед закончился возвращением в стойку **до начала** первого намеренно неполного приседа. Уточнённую границу `29,35` выбрали из временного промежутка между окончанием этого движения и началом следующего. Исходную разметку не переписывали, приватная откорректированная копия хранится только в пользовательском чате. Такая пограничная поправка иллюстрирует зависимость TP/FP/FN от точности разметки — она **не** является дополнительным независимым подтверждением универсальной точности.

В Debug-ветке добавлены 4 синтетических XCTest для одиночного пропуска confidence, устойчивой потери, отсутствия ложного повтора после двух кадров сгибания и явного reset. Не делать merge до Xcode `⌘U`, успешного Swift Replay на четырёх JSON и отдельной проверки на новом видео/ракурсе. Порог ТК `+0,35` и PR #32 не менялись.


## Разбор оставшихся FN и независимый асимметричный Replay (20.11.2026)

Повторный анализ **двух приватных размеченных файлов от 19.11** показал:
- Три пропуска: legacy постоянно отслеживал правую ногу со стабильным коленным углом около 155–165°, когда левая уходила в 70–73° и проходила прежний порог глубины.
- Два пропуска: во время глубокого движения переключение/потеря надёжности ноги сбрасывало фазу или не позволяло заново подтвердить стойку. На первом файле у одной попытки восстановленный independent-leg count находится в **t=32,332 с**, на 32 мс ПОЗЖЕ конца annotation `32,300 с`. Нельзя самостоятельно расширять annotation без повторного просмотра исходного видео.

В PR #28 добавлен **отдельный теневой** `PoseReplayAsymmetricDepthAudit.replay(session)` (не влияет на live счётчик, main, production порог и PR #32):
- Сначала воспроизводится уже существующий Grace Replay (он остаётся baseline для нового сравнения).
- Параллельно независимо обрабатываются две ноги отдельными `SquatCounter`, с удержанием ненадёжных кадров до 0,23 с без их использования для подтверждения.
- Дополнительный самостоятельный кандидат принимается только если собственная нога надёжно сгибалась до 105° и проходила ТК≤+0,35, высота hip–ankle относительно её калиброванной стойки уменьшалась на ≥44%, а в том же надёжном кадре другая нога визуально была ≥145° по колену. Эти условия нужны для явной асимметрии 2D перспективы и не являются универсальной биомеханической истиной.
- Подтверждённое дополнительное событие не добавляется, если другой подсчёт находится в пределах ±0,75 с. Дедупликация по времени **не гарантирует** корректность на быстрых повторениях, поэтому пока только в Replay.
- В импортном Debug HUD появились строки `Асимметрия 2D (тень)`, `Доп. кандидатов`, при annotations — `Асимметрия TP/FP/FN`. Добавлены 5 синтетических XCTest, включая проверку, что scorer НЕ скрывает пограничный FP.

## Восстановление при перекрытии и разнице проекций (Issue #34)

При импорте в Debug строка «Восстановление при перекрытии» показывает сумму исходных событий и экспериментальных дополнений. Ниже выводится время каждого дополнения в секундах от REC. На файле с ручной разметкой можно сравнить TP/FP/FN обоих вариантов в одном окне.

**Как принимается решение**

- Для дополнительного цикла нужны три кадра стойки с двумя надёжными ногами и подтверждённая фаза `standing` исходного счётчика. Высота тазобедренного сустава над лодыжкой в этой стойке служит масштабом отдельно для каждой стороны. Исходные события, включая возврат после старта REC в фазе `lowered` в JSON v2, сохраняют свои метки времени.
- Глубину подтверждают три реальных наблюдения одной ноги. Нужны угол колена ≤105°, ТК ≤0,35 и уменьшение высоты тазобедренного сустава над лодыжкой минимум на 44%. Для завершения серии требуется опускание второй стороны минимум на 34%.
- Если исходный анализатор переключился с этой ноги, можно удержать два наблюдения глубины или уже подтверждённый низ. От последнего надёжного наблюдения до возвращения ноги допускается до 0,8 с. На каждом кадре перекрытия должна оставаться видна другая нога с опусканием ≥44% либо с опусканием ≥34% и углом колена ≤105°. При 2/3 третье наблюдение должна дать вернувшаяся нога.
- Отдельный случай для 2/3: если в кадре переключения вторая нога уже надёжно опустилась на ≥34%, но сильного подтверждения ещё нет, серия временно сохраняется. До возвращения исходной ноги нужны по меньшей мере два последовательных наблюдения с сильной поддержкой. Каждый кадр после переключения, включая кадр возвращения, должен пройти прежнюю проверку поддержки. Возвращённая нога сама должна подтвердить глубину. Весь интервал ограничен 0,5 с от последнего надёжного измерения исходной ноги. Кадры с потерянным суставом дают только сведения о второй стороне.
- Если обе ноги видны, выбранная сторона может устойчиво не проходить порог угла или ТК. Для дополнения нужны три последовательных кадра, на каждом из которых противоположная сторона проходит глубину, а выбранная даёт указанное выше подтверждение опускания.
- Для зачёта нужны три кадра возврата обеих ног до ≥160° и ≥80% их исходной высоты. Эксперимент ждёт фазу `standing` базового счётчика. Если он уже засчитал повтор в этом цикле, приоритет получает его метка. Две последовательные попытки разделяет подтверждённая стойка.
- Сброс, пустая поза, потеря обеих сторон, вырожденная геометрия, повтор метки времени, разрыв потока >0,25 с или смена ориентации/пропорций разрывают экспериментальный цикл. Окно от стойки ограничено 6 с. Для исключения шагов и поворотов проверяются сдвиг видимых лодыжек и изменение горизонтального расстояния между тазобедренными суставами. Допуск составляет 20% высоты в стойке, для пары берётся меньшая высота.

**Проверка 23 ноября.** При 2/3 подтверждениях слева анализатор переключился на правую ногу в 31,094 с и сбросил движение из `standing` в `seekingStanding`. Шесть кадров имели низкую достоверность левого тазобедренного сустава. Третье надёжное наблюдение глубины получено слева в 31,692 с. Новый Replay сохранил четыре исходные метки и добавил один возврат в 32,988 с. Независимое объединение двух ног дало шесть событий, в том числе два в последующей серии неполных попыток. В предварительной версии эксперимента слабое однокадровое подтверждение второй стороны тоже добавляло событие в этой серии. Проверка одновременной глубины на трёх кадрах устранила его на этой записи. Файл использован при разработке, его массив ручных аннотаций пуст.

**Проверка на новых записях**

1. Зафиксировать версию алгоритма и заранее разметить по видео границы каждой полной и неполной попытки. Отдельно отметить шаги, повороты и перекрытия. Временную шкалу сопоставить по видимым событиям, границы сохранить до прогона.
2. Записать независимые серии для обеих сторон при фронтальном и косом ракурсе, медленном и быстром темпе. Включить потерю бедра и колена по отдельности, перекрытия короче и длиннее 0,8 с, смену стойки, неполный возврат и несколько быстрых повторов подряд.
3. На одинаковых JSON сравнить исходный и экспериментальный Replay. Для каждой серии сохранить TP/FP/FN, дубли в одном интервале, события вне разметки и задержку зачёта от визуального возврата. Отдельно посчитать восстановленные пропуски и вновь добавленные FP по типам движения.
4. До обсуждения рабочего счётчика воспроизвести результат в Xcode и на iPhone. Критерий для следующего обсуждения — уменьшение FN на независимых записях при нуле новых FP и дублей на проверенных отрицательных сценариях. Оптическое смещение суставов при плавном развороте может имитировать двустороннее опускание. Большое движение стоп, длинная пауза внизу или плохо видимая вторая нога могут скрыть настоящий повтор.
