# Pose Replay — воспроизводимая проверка приседаний

## Задача

Изменять алгоритм только после сравнения на **одинаковых входных кадрах**. В этой первой версии Replay фиксирует числовые координаты hip/knee/ankle для обеих ног **после Vision 2D**, то есть поток `BodyPose` непосредственно перед `PoseAnalyzer` и `SquatCounter`. Replay воспроизводит 2D классификацию на тех же координатах и с тем же временем кадров, включая события сброса движения. Экспериментальный Vision 3D из Draft PR #26 **не входит** в эту первую версию.

## Как записать материал на iPhone

1. В Fork открыть ветку `feature/pose-replay-baseline`, в Xcode выполнить `⌘U`, затем Debug `⌘R`.
2. Установить iPhone на устойчивую опору, чтобы **всё тело и ноги** были в кадре. На первом проходе стоять боком к камере. Нажать `Старт`.
3. Нажать кнопку **REC**, прочитать предупреждение о данных о движениях тела, подтвердить `Начать запись`. Запись **не включается автоматически** и не сохраняет фотографии/видеокадры.
4. Постой 2–3 секунды, затем выполни **3 полных, 3 неполных** приседания боком. Встань неподвижно на 2–3 секунды между сериями. При необходимости повернись под 45° и повтори 3+3 (не меняй высоту телефона).
5. Нажми **STOP**, затем выбери `Сохранить в Файлы` или другую опцию системного share sheet. Получится файл `RepsCounter-PoseReplay-….json` c координатами суставов и относительными метками времени. Временный файл приложения удаляется после закрытия меню экспорта.
6. **При желании** одновременно записать экран, чтобы позднее вручную разметить каждую попытку. Видео и экспортированный JSON в GitHub автоматически не отправляются. Для анализа можно передать JSON и видео **отдельно в разговор**, если согласен поделиться числовыми данными тела.

Система записывает **максимум 1200 событий** (примерно две минуты при 10 позах/с). Дальнейшие события не добавляются до STOP. Для длинных сессий начни новый экспорт.

## Что содержит JSON

`schemaVersion: 1`, `events` (время от ручного начала записи, вид `pose` или `reset` и для pose: aspect ratio, угол вращения и координаты/уверенность суставов `leftHip`, `leftKnee`, `leftAnkle`, `rightHip`, `rightKnee`, `rightAnkle`), `annotations` (по умолчанию пустой массив). В данных **нет пикселей камеры, видео или аудио**, но координаты движений тела **являются персональными данными контекста тренировки**, поэтому не публикуй такие файлы в открытом репозитории без явного решения.

`annotations` — необязательные **ручные** временные границы попыток, каждая `{ "startSeconds": ..., "endSeconds": ..., "isFullSquat": true/false }`. Диапазоны неперекрывающиеся. Если приседание физически полное, но алгоритм не засчитал его — FN. Если неполное засчитано — FP. Дополнительное засчитывание в одной полноценной попытке тоже FP. События вне размеченных попыток считаются FP. Пока диапазоны не размечены, **не утверждать precision/recall по числу 2D повторов**.

## Как воспроизводится алгоритм

`PoseReplayRunner.replay(session)` восстанавливает `BodyPose`, последовательно применяет `PoseAnalyzer` и текущий `SquatCounter(maximumHipKneeHeightRatio: 0.35)`, сбрасывает движение на записанных `reset`, при паузе между пригодными позами более 250 мс и при смене/потере ноги. Выдаёт точные временные метки count и диагностические `PoseReplayDepthSample`.

**Теневая проверка глубины** хранит `signedHipKneeVerticalDistance = hip.y - knee.y` по выбранной 2D ноге в нормированных координатах Vision (Y растёт вверх): значение положительно, пока **центр hip-joint выше knee-joint**; <=0 означает что эти два распознанных центра на одной высоте или тазобедренный центр ниже. Это **ещё не** биомеханический критерий «складка таза ниже верхней части колена»: 2D перспектива и неточность суставов влияют на метрику. Сравниваются **непосредственно** signed distance и старый нормализованный наклон бедра, но оба значения **не влияют на счёт**.

`PoseReplayRunner.score(result, against: annotations)` вычисляет TP, FP, FN только на вручную размеченных диапазонах. В тестовом наборе есть демонстрационные синтетические позы; они подтверждают детерминированность и корректность инфраструктуры, но **не реальную accuracy Vision**.

## Границы первой версии

- Реплей выполняется над **после-Vision 2D** наблюдениями: он не измеряет ошибки самого Vision от видеопикселей. Чтобы исследовать точность распознавания суставов, нужны визуальные референсы, полученные с отдельным явным согласием, и разметка.
- В этом PR не меняются production 2D счёт, порог 0,35, камера, Core Data или экспериментальный 3D.
- Следующим этапом после получения первого реального JSON и ручной разметки можно расширить формат до синхронных 3D числовых показателей отдельным небольшим PR (не добавлять 3D через прямое копирование 61-коммитного Draft #26).
- В Xcode обязательны `⌘U` и `Product → Build For → Profiling`; Release не содержит инструментов Replay.

## Второй этап — независимый двухногий Replay (19.11.2026)

В этой же Debug-ветке появился `PoseReplayBilateralRunner.replay(session)`. Он **не подключён к экранному счётчику, истории или Vision 3D**. На том же JSON он сначала воспроизводит исходный `PoseReplayRunner` для контрольного результата, затем независимо пропускает позы левой и правой ноги через свои `PoseAnalyzer` и `SquatCounter(maximumHipKneeHeightRatio: 0.35)` с прежними требованиями confidence, 3 кадрами подтверждения, EMA и сбросом после gap >250 мс.

Для каждого потенциального подсчёта сохраняется сторона, момент подтверждения глубины и момент завершения повторения. События от **разных ног** объединяются в одно, только если их интервалы от подтверждённой нижней фазы до возврата действительно пересекаются, а окончания разделяет не более **0,75 с**. События одной и той же ноги никогда не объединяются. Это **эвристика дедупликации**; на другом темпе и при долгом залипании фазы она может потребовать изменения по размеченным данным. Агрегатор не пересматривает критерии глубины и не выбирает «правильную» ногу по 2D confidence.

### Повторная проверка JSON без Terminal

В Debug на экране тренировки **нажми и удерживай кнопку `REC`** (не обычное короткое нажатие). В контекстном меню выбери **`Открыть Replay JSON`**, затем в системном приложении «Файлы» выбери ранее сохранённый JSON. Приложение проанализирует файл **только локально**, не начнёт новую тренировку и покажет системное окно со значениями: `Обычный 2D`, `Левая нога`, `Правая нога`, `Объединено` и `Убрано дублей`. Файл читается только по действию пользователя и **не превышает 10 МБ**. Пока идёт новая REC-запись, импорт заблокирован до STOP.

На первой пользовательской записи ожидаемый результат по независимой предварительной репродукции — **3 / 2 / 3 / 5 / 0** соответственно. Это **ожидание для проверки реализации Swift**, а не уже подтверждённый запуск Swift на этом устройстве. Если расхождение появится, сохранить скриншот вывода и проверить симулятор/порядок событий в Xcode прежде любых изменений порогов.

Если `annotations` пусты, окно прямо говорит, что точность неизвестна. Если файл содержит валидные вручную размеченные диапазоны, дополнительно показываются TP/FP/FN для исходного и объединённого вариантов.

**Критерий следующего этапа:** пройти полный `⌘U` в Xcode, открыть сохранённый JSON через долгое нажатие REC и сверить результат с таблицей. Затем, после разметки физических попыток, сравнить фактические TP/FN/FP на нескольких записях, прежде чем менять production.


## Аудит глубины по размеченным числовым записям (20.11.2026)

В Debug реализован `PoseReplayDepthAudit.evaluate(session)`. После импорта **локального JSON с `annotations`** он показывает, насколько часто **нижняя фаза** подтверждается по каждому из трёх независимых диагностических правил:

- **Только угол:** коленный угол ≤105° минимум в трёх последовательных достоверных кадрах одной и той же ноги.
- **Текущий проекционный ТК:** угол ≤105° и `(hip.y-knee.y)/projectedThighLength ≤+0.35`, три последовательных достоверных кадра.
- **Центр hip не выше центра knee:** угол ≤105° и `hip.y-knee.y ≤0`, те же три последовательных кадра.

Для каждой ноги минимальная confidence hip/knee/ankle — 0,5. Пропуск/сброс или разрыв более 0,25 с прерывает серию. Сравниваются обе ноги независимо; признак наличия нижней фазы в размеченной попытке считается, если один из анализаторов подтвердил её. **Это не реальный FSM-count**: нет отдельной проверки возврата в стойку, EMA/фьюжна и дедупликации. Результаты нельзя интерпретировать как точный TP/FP/FN production-счётчика.

Для **двух локально размеченных** сессий 19.11.2026 (всего 24 попытки: 12 отмечены полными, 12 неполными) независимый Python-аудит этих же порогов дал:

| Правило нижней фазы | Полных с нижней фазой (из 12) | Неполных ошибочно с нижней фазой (из 12) |
| --- | ---: | ---: |
| Только угол ≤105° | 12 | 12 |
| Угол + текущий ТК ≤+0,35 | 11 | 0 |
| Угол + hip.y ≤ knee.y | 0 | 0 |

Числовые записи, суставные координаты и привязанные к ним временные метки **не добавлены в GitHub**. Приведены только агрегированные результаты. Разметка пользовательская, не измерение референтной биомеханической глубины; две сессии не охватывают проблемный ракурс и тесты от 20.11.2026. На другом ракурсе текущий ТК может ошибочно отклонять полные приседания.

**Вывод:** простое ослабление порога или замена ТК строгим `hip.y ≤ knee.y` не обоснованы. Прежде чем менять production, собрать новый **размеченный числовой Pose Replay** именно для ракурса 15–20° от фронта и повторить A/B на одних входных наблюдениях. Результаты текущей реализации оценивать через `⌘U` и импорт JSON на iPhone. Результаты XCTest/Release после этого обновления ещё не подтверждены.


## Теневой адаптивный критерий глубины (20.11.2026)

Новая функция `PoseReplayAdaptiveDepthAudit.replay(session)` доступна **только в Debug Replay**. Она не изменяет счётчик тренировки, `SquatCounter`, порог production ТК +0,35, историю, камеру, 3D и другие ветки. В результате импорта JSON отображаются `Адаптивный 2D (тень)` и `Доп. кадров глубины`; при наличии ручных annotations дополнительно показываются `Адаптивный TP/FP/FN`.

Механизм: исходная FSM и EMA остаются прежними, стандартный критерий `ТК≤+0,35` принимается без дополнительных требований. Для кадров с `+0,35 < ТК ≤+0,45` возможна **альтернативная проверка**, только если одновременно:
- обе ноги распознаны достоверно (hip/knee/ankle confidence ≥0,5), и угол каждого колена ≤105°;
- после предварительно распознанной стойки (колено ≥160°) нормализованное уменьшение вертикального расстояния hip–ankle на **каждой ноге** ≥0,34 относительно её собственной медленно обновляемой опорной высоты;
- условия выполняются **не менее трёх последовательных кадров**; сбросы и большие разрывы обнуляют накопление и стойку.

Только в локальном теневом `SquatCounter` при выполнении условий используется виртуально подтверждённый ТК=+0,35. Исходная геометрия и само наблюдение не модифицируются. Это **эвристика оценки по 2D проекции**, а не физический стандарт «складка таза ниже верхней части колена». При перекрытии второй ноги функция может не улучшать recall, потому что усиление допускается лишь при двух надёжных ногах.

### Предварительная проверка на трёх пользовательских JSON

Независимый офлайн Python-перенос предлагаемой логики повторил тест на реальных событиях до реализации в Swift. Сырые координаты и видео не добавлялись в репозиторий.

| Набор | Legacy TP/FP/FN | Adaptive TP/FP/FN | Число событий |
|---|---|---|---|
| 19.11, размеченный №1 (12 попыток) | 3/0/3 | 3/0/3 | 3 → 3 |
| 19.11, размеченный №2 (12 попыток) | 4/0/2 | 4/0/2 | 4 → 4 |
| 20.11, косо-фронтальный (519 событий, без annotations) | нет разметки | нет разметки | 0 → 5 |

Последняя строка — **прогноз теневого Replay**, не 5 подтверждённых true positives. Всего старые наборы содержат 12 полных и 12 неполных попыток; их результаты не ухудшились, но и пять существующих FN не были устранены. Параметры +0,45, 0,34 и 3 кадра являются экспериментальными и не валидированы на независимой выборке. Результаты Swift на реальном JSON, Xcode XCTest и Release Build **ещё не подтверждены**.
