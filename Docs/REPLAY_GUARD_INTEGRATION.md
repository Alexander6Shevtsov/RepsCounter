# Интеграционная проверка Pose Replay и Guard

Ветка: `test/issue-27-replay-guard-integration`. База — Draft PR #28 (`feature/pose-replay-baseline`). Контрольный 2H-Guard скопирован **без изменения логики** из Draft PR #32 (`fix/issue-27-bilateral-conflict-guard`).

## Область эксперимента

Это **сравнение алгоритмов на одном и том же потоке поз**, а не один объединённый production-счётчик. Replay независимо вычисляет:

- исходный 2D (`PoseReplayRunner`);
- Adaptive и Grace (`PoseReplayAdaptiveDepthAudit`);
- Asymmetric (`PoseReplayAsymmetricDepthAudit`);
- 2H Guard (`BilateralLiveCounter` из PR #32).

В `PoseReplayGuardIntegrationAudit` Guard получает исходные числовые позы и отметки времени, включая события `reset` и разрывы потока. Отложенные подтверждения считаются по моменту завершения движения `countedAt`, **не по моменту flush**. `finishPending()` вызывается в конце Replay и при явном сбросе. Так можно корректно сравнивать Guard с временной разметкой TP/FP/FN.

В Debug-окне импорта дополнительно отображаются `Guard 2H (тень)`, `Guard откл.: Л … · П …`, `Guard дублей` и `Guard 2H TP/FP/FN`, когда annotations присутствуют. Исходный режим тренировки, история, камера, пороги ТК и счётчик **не меняются**.

## Добавленные XCTest (17)

1. Один полный присед двумя ногами — ровно одно событие и одно объединение дубликата.
2. Полный, затем намеренно неглубокий — ни одного лишнего.
3. Кандидат слева при достоверном противоречии правой ноги — отклонён.
4. Аналогичное противоречие слева для правого кандидата.
5. Ненадёжная вторая нога — допустимый single-leg fallback.
6. Одна пропущенная поза — сохранение корректного события Guard и Grace.
7. Серия пропущенных поз — запрет позднего досчёта.
8. Явный `reset` в нижней фазе — нет склеивания движения.
9. Разрыв кадров более 0,25 с — нет склеивания движения.
10. Быстрые повторения — без двойного подсчёта.
11. Отложенное событие при завершении Replay — учитывается один раз.
12. TP/FP/FN с исходной временной меткой `countedAt`, не с задержкой commit.

## Теневой Guard с проекционной геометрией

В ветке PR #33 добавлен альтернативный Debug policy `BilateralGuardPolicy.calibratedProjection`. Исходный `BilateralLiveCounter()` по умолчанию использует `.strict`, сохраняя Guard PR #32 без изменений для рабочего поведения.

Сначала применяется неизменённое правило PR #32: 3+ надёжных измерения противоположного колена в окне нижней фазы и все >105° означают противоречие. В экспериментальном режиме такое отклонение **может быть отменено** только при одновременном выполнении всех условий:

1. Не менее трёх кадров в исходной стойке (колено ≥160°) позволили калибровать вертикальную hip–ankle высоту отслеживаемой ноги.
2. В пределах окна `[loweredAt−0,55; min(countedAt, loweredAt+0,55)]` зафиксировано не менее трёх надёжных кадров кандидата с коленом ≤105° и обычным TK≤+0,35.
3. Максимальное нормализованное снижение hip–ankle высоты кандидата на этих кадрах составляет ≥44% относительно исходной стойки.
4. Противоположная нога дала минимум три надёжных измерения и **каждый** угол в том же окне был ≥120°. Если эта нога иногда сгибается заметнее, сохраняем исходное отклонение Guard.

Ненадёжные кадры не используются для доказательства глубины. Состояние обнуляется при reset / большом пропуске. Все правила применяются только в новом `Guard+геометрия (тень)` при локальном Debug Replay, не в реальном счётчике.

**Обнаруженная причина:** критерий «hip–ankle descent ≥44%» **сам по себе даёт 5 FP** на почти-фронтальной неполной серии; противоположное колено на этих ложных движениях имело min ~108–111° в наблюдаемом окне, поэтому дополнительная проверка ≥120° сохраняет запрет. В данном наборе полные движения, которые ошибочно отклонял строгий Guard, сохраняли opposite knee ≥122° в тех же окнах. Порог 120° подобран по уже просмотренным данным и **не является общим физиологическим критерием**.

Полный присед на фронтальной записи всё ещё пропущен даже новым Guard: отсутствует корректный кандидат в нижележащем `BilateralLegTracker`, поправка отклонения его не создаёт. Это сравнение **не означает готовность к production** и не заменяет независимые тесты на разных людях/ракурсах.

Для Debug-импорта добавлены строки `Guard+геометрия (тень)`, `Guard+геометрия откл.` и `Guard+геометрия TP/FP/FN`. Созданы ещё пять синтетических XCTest: восстановление ложного отказа, сохранение отказа при сгибании другой ноги, обязательная калибровка высоты, отсутствие двойного счёта и запрет перехода через reset. Ни сырые координаты, ни видео пользователя в GitHub не коммитятся.

## Проверка

1. В Fork сделать Fetch и Checkout ветки `test/issue-27-replay-guard-integration`, затем Pull, если требуется.
2. В Xcode выбрать Debug, запустить `⌘U`. Нужны успешные все XCTest, прежде всего `ReplayGuardIntegrationTests`.
3. В Debug на iPhone удержать REC, импортировать **размеченный JSON** и сравнить строки `Guard 2H` с независимыми результатами. Личные видео и координаты не передавать на GitHub.
4. В Xcode выбрать iOS Simulator → Product → Scheme → Edit Scheme → Run → Build Configuration = **Release** → Product → Build (`⌘B`). Проверить `Build Succeeded`. Затем вернуть Run → **Debug**.
5. Не объединять PR #28, #32 или эту ветку в `main` до положительного результата Xcode и проверки реальных Replay.

### Ограничения

- Xcode/iOS-компилятор недоступен в серверной среде, поэтому новая интеграционная ветка **пока не имеет подтверждённого XCTest/Release Build**.
- Эти 12 сценариев синтетические; реальный iPhone, качество Vision и распределение шумов поз требуют отдельной проверки.
- Предыдущие пять размеченных записей использовались при подборе Adaptive/Grace/Asymmetric. Они не являются независимым подтверждением общей точности.
- Эта ветка не является готовым merge Adaptive+Grace+Asymmetric+Guard в рабочем приложении: до него необходима отдельная архитектура fusion, тесты на real-world FP и безопасный rollout.
