# Камера: конкурентность и жизненный цикл

Статус: **In Development**. Этап №5, A02/A06, ветка `fix/camera-lifecycle` от `main` (`a134e81`, объединённый PR №3). Изменения этой ветки требуют ревью; аппаратная проверка не выполнена.

## Контексты исполнения

- `CameraService` изолирован MainActor: разрешения, состояние, отмена запуска и допуск результатов к UIKit. `WorkoutCameraCoordinator` согласует его с MainActor-моделью тренировки. Два узких контракта — `CameraAuthorizing` и `CameraCapturing` — позволяют подменять разрешения и захват без физической камеры.
- `CameraCapture` — actor с собственным executor на `DispatchSerialQueue`. Только он конфигурирует `AVCaptureSession`, проверяет `isRunning` и вызывает `startRunning`/`stopRunning`. Внутри конфигурации и запуска нет точек `await`; команды не пересекаются и выполняются вне MainActor. Возраст команды проверяется по монотонному номеру поколения.
- Отдельная serial queue принимает `CMSampleBuffer` и синхронно выполняет Vision. Новый delegate создаётся для каждого поколения. Его `PoseDetector` и изменяемое состояние принадлежат `OSAllocatedUnfairLock`; `invalidate` сериализуется с текущим распознаванием. Raw buffers и Vision request не пересекают границы изоляции.
- В MainActor передаётся только `Sendable`-значение: `BodyPose?`, поколение и монотонная отметка времени. `alwaysDiscardsLateVideoFrames`, интервал анализа 80 мс и `AsyncStream.bufferingNewest(1)` ограничивают накопление кадров. На входе в MainActor отклоняются старое поколение, результаты старше 250 мс с момента начала анализа, повторные/переставленные отметки и кадры после stop/finish. Возраст исходного sensor buffer отдельно не измеряется; сброс поздних входных кадров выполняет AVFoundation.
- События сессии используют отдельный поток без вытеснения кадровыми результатами. Наблюдатель извлекает из `Notification` только тип события и строку ошибки; сам `Notification`/`NSError` между исполнителями не передаётся.

Это следует подходу Apple с actor для блокирующих операций захвата: [AVCam](https://developer.apple.com/documentation/avfoundation/avcam-building-a-camera-app). Пример привязки actor к serial executor приведён в [Camera Control](https://developer.apple.com/documentation/avfoundation/enhancing-your-app-experience-with-the-camera-control). Использованные API executor доступны с iOS 17; deployment target и Swift language mode проекта сохранены.

## Единственная граница `@unchecked Sendable`

`CameraPreviewSource` — небольшой immutable bridge к `AVCaptureVideoPreviewLayer`. SDK не объявляет `AVCaptureSession` как Sendable, но preview должен использовать ту же сессию, которой владеет actor. Bridge скрывает ссылку `private let session` и предоставляет только MainActor-метод присоединения слоя. Контроллер вызывает его в `viewDidLoad` до первого запуска. Ни session, ни её методы конфигурации/старта/остановки через bridge не выдаются. Управление сессией остаётся исключительно у `CameraCapture`; preview обслуживается AVFoundation.

Это локальное допущение для штатной связи session/preview, а не аннотация всего camera service. Корректность вывода и поведения AVFoundation под нагрузкой ещё нужно подтвердить на iPhone. `@preconcurrency import` для подавления диагностики не используется.

`OSAllocatedUnfairLock(uncheckedState:)` хранит непередаваемые `PoseDetector` и observer tokens внутри закрытого состояния. Синхронный `withLockUnchecked` нужен только там, где closure захватывает raw buffer или session при регистрации наблюдателей. Closure не сохраняется и не отправляется на другой executor; состояние и Vision request не выходят из lock. Остальные обращения используют `withLock`. Это явное ограничение области владения, а не передача buffer как Sendable.

## Запуск, отмена и восстановление

Первый запуск ожидает разрешение и фактический успех `startRunning`. Одновременные start используют одну операцию. Запрос разрешения повторно не создаётся даже для start → stop → start, пока системный запрос ещё ожидает ответа. Stop немедленно меняет поколение на MainActor и отменяет ожидающий start, затем останавливает backend. Прямая отмена возвращённой Task через cancellation handler также переводит управление в stop, не ожидая ответа разрешения; сам системный запрос может завершиться позднее. Более старые start/stop не могут изменить новое поколение.

Finish — терминальное состояние: новые start и кадры игнорируются; отменяются операции и задачи чтения обоих потоков. Backend снимает delegate, останавливает сессию, удаляет observer tokens и завершает потоки. Повторный finish возвращает ту же задачу освобождения. Deinit не удерживается задачами чтения и инициирует такую же очистку. Обычная пауза останавливает захват, сохраняя наблюдение за событиями до повторного запуска или finish.

Системное окно разрешений нельзя программно закрыть отменой Swift Task. Поздний ответ не запускает завершённую тренировку. Уже начавшийся синхронный `startRunning` также нельзя прервать внутри SDK: отмена проверяется перед вызовом и после возврата, после чего сессия останавливается. Готовность, активное время и результаты такого отменённого запуска не публикуются.

Отказ показывает русскую инструкцию. После возврата из Settings статус перечитывается, но камера и тренировка ждут «Продолжить». Background вызывает паузу и stop; foreground только обновляет доступность разрешения. `wasInterrupted` и runtime error приостанавливают тренировку, прекращают допуск кадров и останавливают сессию. `interruptionEnded` снимает состояние прерывания без автоматического запуска. Временная ошибка допускает явный повтор; сообщение для пользователя русское, техническая строка остаётся в состоянии сервиса.

## Согласование с тренировкой

Production composition создаёт `WorkoutViewModel(cameraReady: false)`: до готовности камеры активное время равно нулю. `setCameraReady(true)` само не продолжает тренировку — это делает coordinator только для первоначального запроса или явного действия пользователя. Отдельные `pause` и `resume` идемпотентны; повторный lifecycle event не превращает паузу в продолжение.

Пауза использует прежние `resetMovement` и сброс сглаживания. Сохраняются засчитанные повторения, подходы и дробная активная длительность. После продолжения нужно заново подтвердить standing. Отдых использует прежнюю шкалу активного времени и замораживается вместе с ней. Завершённая UUID-сводка и повтор сохранения не меняются. Core Data, схема, `WorkoutSummary`, `SquatCounter`, `PoseAnalyzer` и `PoseDetector` не изменены.

Минимальное изменение UI — прежняя подсказка показывает подготовку/ошибку/паузу, а существующая кнопка «Продолжить» выполняет явный повтор. Она недоступна во время ожидания разрешения и запуска; «Завершить» доступно. Разметка и оформление сохранены.

## Что проверяет XCTest

Детерминированные зависимости управляют ответом разрешения, задержкой/ошибкой backend и монотонным временем; временные сценарии не используют `Task.sleep`. Await дожидается конкретной операции или сигнала; таймаут XCTest используется только как ограничитель доставки потокового события.

| Требование | Покрытие |
|---|---|
| Успешный start, первый grant, denial | `CameraLifecycleTests` |
| Settings и повторный start без дублирования | Оба новых набора |
| Stop/cancel/finish до ответа разрешения и во время start | Оба новых набора; start → stop → start в обоих ожидающих состояниях |
| Background/foreground без автоматического resume | `WorkoutCameraTests`, включая незавершённый запрос разрешения |
| Interruption/end, runtime error, временная ошибка и повтор | Оба новых набора |
| Старое поколение, возраст/порядок результатов, остановленная сессия | `CameraLifecycleTests`, движение после рестарта — `WorkoutCameraTests` |
| Сохранность повторений, новый standing, отдых, быстрый pause/resume/finish и retry UUID | `WorkoutCameraTests` плюс прежние timing/persistence регрессии |
| Потоки, освобождение сервиса/coordinator/ViewModel и удаление наблюдателей | Mock backend, настоящий `NotificationCenter` с `AVCaptureSession` без открытия камеры |
| Русская ошибка и доступный повтор в UIKit | `WorkoutCameraTests.testCameraFailureShowsRussianMessageAndEnablesExplicitRetry` |

Тесты подтверждают управляющую логику и границы передачи значений. Они не подтверждают фактическую работу camera hardware, Vision на видеопотоке, время остановки SDK, точность или отсутствие аппаратных сбоев. Результаты сборок и прогонов приведены в [техническом аудите](TECHNICAL_AUDIT.md).

## Аппаратная проверка на iPhone

- [ ] Чистая установка: первый grant/denial, отсутствие активного времени до готовности, доступность Finish во время запроса.
- [ ] Отказ → Settings → разрешение → возврат: время заморожено, запуск только по «Продолжить»; отдельно проверить отзыв разрешения.
- [ ] Во время приседа и отдыха: Home/блокировка/foreground, неизменные повторения и остаток отдыха, новый standing после явного продолжения.
- [ ] Звонок/системное прерывание/занятость камеры: безопасная пауза, interruptionEnded без resume, допустимый ручной повтор.
- [ ] Реальный runtime error, включая media services reset, если его удаётся воспроизвести: русская ошибка, повтор и отсутствие старых результатов.
- [ ] Быстрые start → stop → start и Pause → Resume → Finish: камера не остаётся включённой после завершения; измерить задержку остановки и индикатор iOS.
- [ ] Finish до ответа разрешения и при уже начавшемся старте: поздний grant не включает завершённую тренировку.
- [ ] Rear camera/portrait: preview, ориентация `.right`, aspect fill и overlay; отсутствие подсчёта незавершённого приседа после рестарта.
- [ ] Ошибка сохранения после прерывания → повтор: те же UUID/длительность/счётчики, одна строка истории и совместимость старых данных.
- [ ] Не менее 10 минут работы и многократные переходы/завершение: Instruments для памяти/гонок, нагрев, задержка Vision, освобождение capture/наблюдателей.
- [ ] iOS 17 и актуальная iOS; Dynamic Type/VoiceOver для нового сообщения, особенно на маленьком экране.

Кадры обрабатываются локально; запись, сетевой обмен и новые сторонние зависимости не добавлены.
