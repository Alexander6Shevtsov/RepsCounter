# Эксперимент 56 — Diagnostic Reliability

База PR #53, e40f5e1182cd7727bf083e5569674d9fff82f646. Ветка debug/issue-34-diagnostic-reliability. Эксперимент 55 остался в отдельной рабочей директории и ветке; дополнительно сохранены patch, архив изменённых файлов и документация в /workspace/work/experiment56. Его новый FSM не включён.

## Часы и источник измерений

| Метка | Источник | Значение |
|---|---|---|
| REC seconds | PoseReplayRecorder получает WorkoutTimeSource.currentTime на MainActor и вычитает значение начала REC | Время записи/обработки после доставки. Это не время съёмки |
| PTS | CMSampleBufferGetPresentationTimeStamp | Исходная рациональная метка камеры: value/timescale/epoch/flags. Сохраняется без округления |
| captureHostSeconds | PTS переводится через synchronizationClock сессии в hostTimeClock | Время захвата на общей монотонной шкале, когда доступно корректное преобразование |
| hostSeconds | PipelineTelemetry.hostNow под блокировкой последовательности событий | Момент диагностического этапа. Порядок sequence сохраняется между очередями |
| delegateHostSeconds | Вход capture callback | Доставка, очередь и планировщик могут менять расстояние между callback |
| recordedHostSeconds | Момент формирования события Pose Replay | Дополнительная диагностическая метка, не замена REC seconds |
| recClockHostBefore/AfterSeconds | Host-часы до и после чтения WorkoutTimeSource.currentTime | Ограничивают неопределённость связи двух шкал. Нельзя выдавать середину этого интервала за точный момент съёмки |

Legacy Live использует фиксированную EMA на измерение и покадровые подтверждения. Время доставки влияет на выбор кадров, максимальный разрыв и REC. Исходный Legacy Replay использует REC seconds и initialState v2. Unified PR #51 на старом Pose Replay использует REC seconds для своих временных окон/EMA. Time-Based эксперимента 54 в живой тени получает measurementSeconds из PTS. Его Replay на обычном JSON по-прежнему использует seconds переданного Replay. Полный Pipeline импортируется через fullPoseSession с PTS, сдвинутым к первому сохранённому входу; оба сравниваемых счётчика получают один поток. Новые cameraPTS не подменяют seconds автоматически.

Для двух событий: deltaREC = deltaCapture + изменение задержки до записи, с погрешностью связи часов. Поэтому наблюдаемые 199.5 мс REC не доказывают ровно такую длительность между экспозициями. Порядок кадров нельзя исправлять сортировкой или создавать отсутствующие наблюдения интерполяцией. UI submit не является временем фактического отображения.

## Запись полного интервала REC

В Debug после явного согласия и REC создаётся отдельная DiagnosticRecordingArchive. Требуется REPS_PIPELINE_TRACE=1. Файлы пишутся в Documents контейнера приложения на отдельной последовательной utility-очереди. На capture/analysis/MainActor пути нет синхронной записи на диск и кодирования всего журнала.

Журнал охватывает события между маркерами recordingStart и recordingStop, то есть интервал записи/доставки. Кадр, захваченный раньше REC и доставленный внутри этого интервала, может входить в журнал с исходным PTS. Результат, завершившийся после STOP, не включается. Это не обещание захватить все экспозиции физической камеры в этом интервале; AVFoundation, Vision, AsyncStream и stale могут терять входы и отражают причины в журнале. Потери этих стадий не выдаются за потерю файла.

Каждое событие между границами отправляется в файловый журнал до вытеснения кольца. Существующее кольцо 8192 остаётся окном метрик вне REC и не является источником полного архива. Текущий неполный snapshot больше не экспортируется вместо завершённого REC: после REC экспорт истории использует полный архив. Во время REC он просит сначала остановить запись.

Объём памяти очереди ограничен 256 ожидающими элементами; один элемент имеет ограниченные данные одного кадра. Переполнение не блокирует камеру: запись немедленно получает ошибку полноты, последующие элементы отклоняются с подсчётом. Сборка JSON и запись/закрытие находятся на фоновой очереди. Нет конечного лимита продолжительности REC или 1200 событий для архива; объём диска растёт с длительностью. При нехватке диска или ошибке ввода-вывода полный результат не объявляется успешным. Нужно заранее проверить свободное место, а не рассчитывать на бесконечную запись при ограниченном хранилище.

Сохраняются два файла с одним recordingID: Pipeline и PoseReplay. Старое превью PoseReplayRecorder остаётся ограниченным 1200 событиями. При превышении оно отказывается экспортироваться как полная запись. Завершение через UI дожидается фонового закрытия двух полных файлов и предлагает поделиться обоими URL. Пока прежняя запись не закрыта, следующая не начинается. Разъединение камеры закрывает активный архив. Записи не удаляются автоматически.

При нормальном STOP в конце каждого файла находится статус complete, числа записанных событий, число отклонённых событий, причина ошибки и stoppedHostSeconds. Полнота означает отсутствие потери журнала между его маркерами, а не идеальность Vision. При завершении процесса/сбое до STOP footer может отсутствовать: такой файл невалиден как полный JSON и не должен считаться завершённым. Успешное закрытие включает synchronize; это не защита от любой аппаратной потери питания.

## Форматы и сопоставление

Pipeline-файл архива имеет traceVersion 4, recording metadata и archiveStatus. Полные события содержат recordingID, trace id находится в корне, кадр содержит generation/camera/frame id, исходный PTS и host-времена. Перечень событий непрерывен по sequence. totals относятся к интервалу REC. elapsedMS/age/hz в архиве намеренно пусты: они не копируются из усечённого кольца. Их следует вычислять по полным событиям; отдельные elapsedMS и ageFromPTS_MS сохранены на каждом этапе.

PoseReplay остаётся schemaVersion 1/2 с дополнительными необязательными recording/diagnosticStatus и полями cameraPTS/captureHostSeconds/recordedHostSeconds/recordingID/host-bracket в событиях. seconds, порядок, initialState и счётчик не меняются. Для кадра используйте тройку traceID + recordingID + pipelineFrameID. Разные REC одного запуска имеют разные recordingID. Для reset без кадра сопоставляйте маркер replayRecorded и REC seconds, не придумывайте PTS. Если reset связан с текущим кадром, его cameraPTS описывает этот кадр, а не отдельную экспозицию reset.

Неполный статус, несогласованный recordingID, traceID или число событий отбраковываются диагностическим импортом. Старые файлы без этих дополнительных полей продолжают читаться. Snapshot v1–3 остаётся снимком окна; UI явно показывает число вытесненных событий. Отсутствующий старый статус не превращается в подтверждение полной записи.

Текущий безопасный GUI-импорт Replay сохраняет лимиты 10 МБ и 1200 событий. Более длинный полный архив сохраняется на диск целиком, но не импортируется этим ограниченным анализатором целиком. Для него нужен отдельный потоковый анализатор с переносом состояния между блоками. Это ограничение анализа, а не усечение сохранённого источника. Не делите запись на независимые Replay, сбрасывая FSM на каждом блоке, и не называйте результат эквивалентным.

## Build provenance и проверка dirty через Fork

buildSHA — HEAD Git в момент сборочного шага, не SHA бинарного файла. sourceState вычисляется из git status --porcelain и включает staged, unstaged и неигнорируемые untracked-файлы. patchSHA — SHA-256 git diff HEAD --binary: tracked staged + unstaged, без untracked. Строка теперь нормализована до одного хеша без суффикса `  -`.

Дополнительный CameraQualityBuildAudit.txt содержит время сборки UTC, перечень tracked-изменений, количество untracked и fingerprint содержимого tracked/untracked файлов приложения, тестов и проекта. Он включён в recording metadata. Наличие неотслеживаемого файла может дать dirty при пустом tracked diff; это не доказательство изменения алгоритма. Fingerprint — снимок файлов в момент шага, не доказательство всех фактических входов компилятора, особенно если файлы редактировались во время сборки.

В старой установленной сборке e40f5e1 указан один patchSHA, совпадающий с предыдущими тестами качества, но самого патча нет. Его конкретную причину установить нельзя. Возможные причины: Xcode изменил DEVELOPMENT_TEAM, bundle id, provisioning/signing в project.pbxproj, tracked scheme либо другую отслеживаемую настройку; остались staged-изменения или неигнорируемые новые файлы. Игнорируемые xcuserdata сами по себе dirty не создают.

Проверка без терминала:

1. В Fork откройте репозиторий. В истории выберите коммит базы и скопируйте полный SHA. Проверьте текущую ветку. Не переключайтесь поверх незавершённого эксперимента 55; используйте отдельную рабочую копию 56.
2. До запуска Xcode откройте Local Changes. Просмотрите отдельно staged, unstaged и untracked. Сохраните список и содержимое Diff. Не используйте Discard для очистки чужих изменений.
3. Откройте проект в Xcode, задайте команду подписи и устройство. Вернитесь в Fork и обновите статус. Сравните изменения, особенно project.pbxproj, со снимком до открытия Xcode.
4. Выполните сборку без редактирования файлов во время неё. Снова проверьте Fork после сборки. Разница между снимками показывает изменения Xcode, но остаётся отдельно от уже имевшихся локальных изменений.
5. На стартовом Debug-экране проверьте HEAD и dirty/clean. В сохранённом файле проверьте recording.buildSHA/sourceState/patchSHA/buildAudit. Совпадение только HEAD недостаточно для подтверждения равенства сборок.
6. Для изучения audit-ресурса и файлов после ошибки: Xcode → Window → Devices and Simulators → iPhone → Installed Apps → RepsCounter → Download Container. В Finder откройте содержимое контейнера; журналы находятся в Documents. Файлы остаются приватными. Новая сборка не изменяет происхождение старого dirty-файла.

## Живой тест

1. Выполните полный Product → Test на Mac и Release Build. Для тестов запись архива включается только явной инъекцией; переменная трассы сама по себе не переводит unit-тесты в режим файловой записи.
2. Run → Debug, REPS_PIPELINE_TRACE=1. Запустите приложение, выберите настройки камеры, начните тренировку, нажмите REC и подтвердите запись всех суставов. Для чистого сравнения стойте секунду перед первым движением и после последнего.
3. Сделайте короткую серию, затем длинную, превышающую прежнее окно кольца и 1200 входов Live. Можно оставить REC во время паузы/возобновления и смены камеры. Проверяйте объём свободного диска.
4. Нажмите STOP. Дождитесь результата закрытия. Сохраните ОБА файла из одного диалога. recordingID должен совпасть, complete должен быть true, rejectedEvents — 0. Начало должно содержать recordingStart, конец — recordingStop; число событий должно совпадать со статусом.
5. Внутри интервала проверьте непрерывность sequence, связь кадров между файлами и исходные PTS. Наличие avDropped/streamReplaced/stale анализируйте отдельно: журнал обязан сохранить факт потери, а не создавать заменяющие кадры.
6. Для записи короче лимитов выполните импорт обоих файлов в Debug Replay. Для длинной серии проверяйте полный источник вне ограниченного GUI-импорта. В историю больше не экспортируется поздний снимок кольца вместо полного REC.
7. Отдельно проверьте ошибку завершения, уход в фон и разъединение сцены. Не публикуйте файлы с координатами. После аварийного закрытия незавершённый файл нельзя считать полным.

На устройстве нужно измерить накладные расходы кодирования/записи, размер очереди, скорость роста файлов, CPU, память, thermal state и энергию. Linux-тесты не подтверждают производительность файловой системы iPhone, Xcode SDK-сборку или поведение при принудительном завершении iOS.
