# Профилирование обработки позы на iPhone 15 Pro

Цель измерения — узнать, где кадр теряется или накапливает задержку между захватом изображения, решением счётчика и передачей изменений UIKit. Понадобятся iPhone 15 Pro, Mac, Xcode с поддержкой установленной iOS и Instruments из того же Xcode. Все действия ниже выполняются через графический интерфейс.

## Настройка и проверка сборки

1. Откройте `RepsCounter.xcodeproj`. В навигаторе **Source Control → Repositories → Branches** выберите `debug/issue-34-pipeline-telemetry` и **Check Out**. Для сравнения исходным состоянием служит коммит `582e534` PR #39.
2. Подключите iPhone, подтвердите доверие и включите **Настройки → Конфиденциальность и безопасность → Режим разработчика**, если Xcode этого попросит. В верхней строке Xcode выберите схему **RepsCounter** и физический iPhone. При необходимости в **Signing & Capabilities** выберите свою команду подписи.
3. Выполните **Product → Test**. Откройте последний запуск в **Report Navigator → Test**. Проверьте весь тестовый таргет, включая `PipelineTelemetryTests`, `CameraLifecycleTests` и `CameraSwitchingTests`.
4. В **Product → Scheme → Edit Scheme → Run → Arguments → Environment Variables** добавьте `REPS_PIPELINE_TRACE` со значением `1`. Флажок у строки включает трассу при следующем запуске процесса. Для контрольного прогона снимите его и запустите приложение заново. В **Profile → Info** выберите **Release**. Для Profile включите наследование аргументов и окружения **Run**, если такая настройка доступна. Локальные настройки схемы можно оставить в пользовательской копии схемы.
5. Запустите приложение и предоставьте доступ к камере. При включённой трассе долгое нажатие на кнопку истории в верхней панели открывает пункт **Сохранить трассу обработки**. После прогона выберите его, затем **Сохранить в Файлы → На моём iPhone**. Файл содержит измерения позы и предназначен для приватной проверки. Снимок создаётся по запросу на фоновой задаче. При выключенной трассе пункт отсутствует.
6. Если при запуске из Instruments пункт не появился, в **Edit Scheme → Run → Info** выберите **Release**, запустите через Xcode с включённой переменной, затем **Debug → Detach from Process**. В Instruments укажите iPhone и прикрепитесь к работающему процессу RepsCounter. Для измерения самого запуска используйте **Product → Profile**.

## Сценарий измерения

Запишите версию iOS, версию Xcode, коммит, конфигурацию, камеру, уровень заряда, способ подключения, яркость и режим энергосбережения. Используйте одну ориентацию, освещение и расстояние. Дайте устройству вернуться в исходное тепловое состояние. Экранная запись и открытый диагностический HUD создают дополнительную нагрузку. Если они нужны для отдельной серии, укажите это в результатах.

| Серия | Действия на iPhone | Что сохранить |
|---|---|---|
| Контроль нагрузки | Выполните один и тот же короткий сценарий в Release с трассой выключенной и включённой. Чередуйте порядок, повторите каждую конфигурацию минимум трижды. | CPU, память, пропущенные сроки UI и тепловое состояние по внешним инструментам. |
| Путь одного кадра | Начните тренировку. Покажите пустое поле, стойку, пять обычных и десять быстрых приседаний, затем пять неполных. Повторите с другой стороны и при частичном перекрытии. | Снимок JSON после каждой короткой серии, маркеры этапов и число наблюдений каждого вида. |
| Границы сессии | Приостановите тренировку, возобновите, смените камеру, сверните и верните приложение. Затем сделайте полное повторение. | Причины сбросов, поколения старых и новых кадров, последнее решение перед паузой и первое после неё. |
| Длительная нагрузка | Оставьте тренировку активной на 10–15 минут. Повторите одинаковые короткие серии в начале и в конце. | Профиль памяти во времени, уровень нагрева, частоту и задержки в начале и конце. |
| Стабильность Replay | В Debug поместите приватные Replay в приложение «Файлы». На экране тренировки удерживайте **REC** и выберите **Открыть Replay JSON**. Повторите после перезапуска с другим значением флажка. | Сравните итоги каждого варианта. При включённой трассе `frame.replaySeconds` и `decision.counted` дают исходные моменты решений рабочего Replay. |

В аппаратной серии экспортируйте JSON в конце измеряемого отрезка. Исключите открытие меню, кодирование и диалог «Поделиться» из сравнения CPU и плавности. Храните результаты и файлы Instruments локально.

## Instruments

1. Выберите **Product → Profile**. Для времени CPU откройте **Time Profiler**. Добавьте инструмент **os_signpost** (в некоторых версиях он находится поиском по слову *signpost* в библиотеке **+**). Начните запись, выполните короткую серию, остановите её, сохраните документ через **File → Save**.
2. Выберите процесс RepsCounter и категории `subsystem = RepsCounter`, `category = PosePipeline`. На интервалах **Vision**, **PoseAnalyzer**, **FSM**, **State UI submit**, **Overlay UI submit** видны длительность и номер кадра. Отдельные события **PosePipeline** содержат идентификатор и имя этапа. В **Call Tree** отдельно откройте очередь `repscounter.camera.frames` и главный поток. Запишите время CPU процесса и главного потока, наиболее дорогие стеки Vision, построения состояния UI и наложения скелета. Длительность этапа включает ожидание планировщика внутри интервала.
3. Отдельным прогоном откройте **Allocations**. Запишите исходный *physical footprint* в Memory Gauge или VM Tracker, отметьте поколение в Allocations, повторите сценарий после заполнения кольца, затем несколько раз экспортируйте снимок и закройте диалог. Проверьте живые аллокации и установившееся значение памяти после экспорта. Для поиска объектов, удерживаемых после окончания тренировки, используйте **Memory Graph** в Xcode.
4. Откройте **Animation Hitches** и при необходимости **Core Animation**. Выделите тот же участок движения, зафиксируйте число и продолжительность задержек кадров и частоту обновления, доступную в данной конфигурации дисплея. Сопоставьте их с участками главного потока и маркерами UI. Маркеры приложения заканчиваются при возврате из синхронного обработчика UIKit. Фактическую презентацию композитором исследуйте отдельным инструментом. Для физической задержки «движение → видимое число» нужна независимая видеосъёмка движения и экрана с общим ориентиром.
5. На iOS 26 и новее откройте **Power Profiler**, если его предлагает Instruments для устройства. Сохраните графики системной мощности, дисплея, зарядки и теплового состояния. На более ранней системе используйте доступные **Energy Log** или индикатор **Energy Impact** в Xcode. В JSON `thermalState` содержит начальную категорию iOS и её изменения. Для сравнения энергии задайте одинаковые яркость, состояние зарядки и продолжительность прогонов. Напишите в протоколе, выдал ли инструмент мощность или качественную оценку. [Power Profiler в документации Apple](https://developer.apple.com/documentation/xcode/measuring-your-app-s-power-use-with-power-profiler)
6. Для каждого режима выпишите длительность выбранного участка, число кадров, частоту, p50/p95/p99, CPU, пиковую и установившуюся память, задержки UI, категорию нагрева и показание энергии с единицами. Сохраните разброс повторных прогонов и разницу с выключенной диагностикой. Влияние трассы на устройство устанавливается этим парным измерением.

## Чтение JSON

Файл `RepsCounter-Pipeline-…json` имеет собственный `traceVersion = 1` и UUID запуска `traceID`. Идентификатор кадра возрастает в пределах запуска, в том числе при смене камеры. В `frame` находятся поколение сессии, сторона камеры и точный PTS Core Media (`value`, `timescale`, `epoch`, `flags`). При наличии часов сессии PTS переводится в монотонные часы хоста. Отдельно сохраняется время входа в делегат. Возраст от PTS рассчитывается только для валидной, конечной и непротиворечивой пары времён. Промежуток от захвата до делегата включает работу подсистемы камеры и ожидание вызова. Время постановки в закрытую очередь AVFoundation приложению недоступно. [Часы AVCaptureSession](https://developer.apple.com/documentation/avfoundation/avcapturesession/synchronizationclock)

| Поле или этап | Интерпретация |
|---|---|
| `sequence`, `hostSeconds` | Порядок записи и монотонное время этапа в секундах. Равные значения времени упорядочены по `sequence`. |
| `cameraInput`, `avDropped` | Вызовы `didOutput` и `didDrop`. Для доставленных уведомлений о пропусках сохраняется причина AVFoundation, если она доступна. Разрыв PTS сам по себе не создаёт событие потери. |
| `inactive`, `throttled`, `missingBuffer` | Причины выхода до Vision. Существующий ограничитель допускает обработку с интервалом от 80 мс. |
| `visionStart`, `visionEnd`, `visionPose`, `noPose`, `visionError` | Ожидание до начала запроса, общая длительность вызова детектора и один исход запроса. При частично распознанном теле остаётся `visionPose`. Для исключения сохраняются домен и код. |
| `streamEnqueue`, `streamReplaced`, `streamTerminated`, `serviceReceive` | Попытка передачи, вытеснение предыдущего кадра, передача в закрытый поток, приём главным актором. У вытесненного кадра остаётся его собственный ID. `elapsedMS.serviceReceive` отсчитывается непосредственно перед вызовом `yield`, включая ожидание потребителя. |
| `stale`, `futureFrame`, `outOfOrder`, `wrongGeneration`, `wrongGeometry`, `notRunning` | Отдельные причины отказа CameraService. Длительность проверки отсчитывается от приёма сервисом. Фильтр устаревания использует прежние часы и порог 250 мс. |
| `deliveredPose/Empty`, `processedPose/Empty`, `skipped` | Передача координатору, принятие на обработку моделью тренировки либо причина пропуска. Пустое наблюдение участвует в штатном сбросе состояния. |
| `analyzerEnd`, `decision` | Длительности PoseAnalyzer и FSM. Для каждого решения доступны confidence бедра, колена и голеностопа обеих ног, сырые углы, выбранная сторона до и после анализа, EMA и отношение высоты. Фазы до анализа, при входе в FSM и после решения различают сброс анализатором и переход счётчика. `reason`, `streak` и `counted` объясняют исход. |
| `reset`, `lifecycle`, `thermalState` | Причина сброса, изменение состояния камеры и категория нагрева. События управления между кадрами могут не иметь `frame`. |
| `stateUIEnd`, `overlayEnd` | Завершение передачи состояния тренировки и синхронного обновления слоя позы. `ageFromPTS_MS` здесь — возраст наблюдения при обновлении UI. Один кадр может вызвать несколько обновлений состояния или ни одного. |

`totals` охватывает жизнь процесса. Отсутствующий ключ счётчика означает ноль событий. `events` содержит последние **8192 события**. `overwritten` показывает, сколько более ранних событий отсутствует в снимке, включая перезапись во время копирования. Кольцо не хранит пиксели и исходные координаты. По запросу экспорта оно копируется короткими блоками. Сортировка, вычисление статистик, кодирование и запись выполняются в фоновой задаче.

`elapsedMS` и `ageFromPTS_MS` содержат число образцов и перцентили ближайшего ранга по сохранённым событиям. `hz` по каждому этапу равно `(N − 1) / (последнее время − первое время)` для двух и более разновременных событий. Для частоты запуска Vision используйте `visionStart`, для фактической обработки FSM — `decision`, для непустых обработанных поз — `processedPose`. При короткой выборке p99 может совпасть с максимумом. Чтобы исключить паузы и смешение режимов, выделите в Instruments непрерывную серию одной камеры. Для полной сессии после перезаписи используйте захват Instruments и разности накопительных счётчиков между снимками. Ожидающую передачу на границе снимка учитывайте при сверке итогов.

Pose Replay сохраняет прежние схемы v1/v2 и время от начала REC. В новой записи с диагностикой `pipelineTraceID` связывает Replay с файлом трассы, а `pipelineFrameID` — с реальным кадром. При импорте старого JSON эти поля могут отсутствовать. При повторном вычислении рабочего алгоритма источник обозначается как `replay`, сохраняется `replaySeconds`. Время отдельных команд сброса Replay хранится в `replayControlSeconds`. У статистик и счётчиков офлайн-кадров есть префикс `replay.`. Скорость выполнения импорта описывает локальное вычисление. Из исторического Replay нельзя восстановить PTS камеры, время Vision, потери AVFoundation, нагрев или момент фактического показа на дисплее.
